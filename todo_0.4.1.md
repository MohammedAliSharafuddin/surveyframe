## Bug, FIXED 2026-08-27: the generated Apps Script collector corrupts data on any instrument change

Found 2026-08-27 in the AIC-RSAM study (`AI_Room_service`), whose collector
carries the header comment "Generated by surveyframe (export_google_sheet()
or the SurveyBuilder)". Severity is higher than the `%in%` defect below,
because the failure mode is **silent corruption rather than absence**.

The generated `doPost()` writes the header row only when it creates the
sheet, then builds every row positionally:

```js
if (!sheet) { sheet = ss.insertSheet(SHEET_NAME); sheet.appendRow(EXPECTED_COLUMNS); ... }
const row = EXPECTED_COLUMNS.map(col => data[col] !== undefined ? data[col] : "");
sheet.appendRow(row);
```

Add an item to the instrument mid-collection, regenerate, redeploy, and the
sheet's header is now stale while rows are written in the new order. Every
column from the insertion point onward is off by one. Simulated against a
live 66-column sheet after inserting one profile item:

```
value "Chinese" would have been written to column 7  = header "prof_app_frequency"
value "25_34"   would have been written to column 8  = header "prof_chatbot_prior"
value "Yes"     would have been written to column 50 = header "od_2"
```

Nothing errors. The sheet stays well-formed, `read_responses()` reads it
happily, and the numbers are wrong. A researcher would have no reason to
suspect anything until an analysis made no sense, by which point the affected
rows are indistinguishable from the good ones without knowing the redeploy
date.

Adding an item mid-collection is not an exotic case. It is what a pilot
study does after a face-validity pass, which is exactly how this was found.

**Fix**: make the collector header-driven. Read the live header, append only
columns that are genuinely new, and map every value by name.

```js
let header = [];
if (sheet.getLastRow() > 0 && sheet.getLastColumn() > 0) {
  header = sheet.getRange(1, 1, 1, sheet.getLastColumn()).getValues()[0]
                .map(function (h) { return String(h).trim(); });
  while (header.length && header[header.length - 1] === "") header.pop();
}
if (header.length === 0) {
  header = EXPECTED_COLUMNS.slice();
  sheet.getRange(1, 1, 1, header.length).setValues([header]);
} else {
  const missing = EXPECTED_COLUMNS.filter(function (c) { return header.indexOf(c) === -1; });
  if (missing.length) {
    sheet.getRange(1, header.length + 1, 1, missing.length).setValues([missing]);
    header = header.concat(missing);
  }
}
const row = header.map(function (col) { return data[col] !== undefined ? data[col] : ""; });
```

This keeps existing columns where they are, gives new items their own
column at the right-hand end, and is safe against any future change. A
working version is in
`AI_Room_service/surveyframe_Integration/surveyframe_collector.gs`.

Also worth a line in the docs: a redeploy of the collector after an
instrument change is safe, and why. Right now nothing warns the user either
way.

### Resolution, 2026-08-27

Report confirmed exactly, including the off-by-one shift. Reproduced by
running the shipped `doPost()` against a mock of the Sheets API, with a v1
instrument collecting 1 response, then an item inserted in the middle, the
collector regenerated, and a second response collected:

```
BEFORE  header: [respondent_id, submitted_at, q_freq, q_prior]
        row r2: [r2, t2, Chinese, Weekly, No]
        "Chinese" sits under q_freq, "Weekly" under q_prior, q_language has
        no column at all

AFTER   header: [respondent_id, submitted_at, q_freq, q_prior, q_language]
        row r2: [r2, t2, Weekly, No, Chinese]
        every value under its own header, and no existing column moved
```

The proposed fix was taken as written, with 2 additions. `readHeader_()` and
`styleHeader_()` are separate functions rather than inline, so the header
logic is testable and the header styling that previously only ran at sheet
creation now also applies to a newly appended column. The header is written
with `setValues()` rather than `appendRow()`, so it lands in row 1 of an
existing but empty sheet instead of below whatever is there.

Re-inlined into `inst/builder/survey_builder.html` with
`data-raw/inline_static_template.R`, so the builder's Generate collector
feature emits the fixed version too.

`export_google_sheet()` gains the documentation section the report asked
for, under "Changing the instrument mid-collection", stating plainly that a
redeploy is safe, why, and that it was not safe before 0.4.1, with the advice
to check the header of any sheet collected through a redeployed 0.4.0
collector.

**Regression test**: `tests/testthat/test-collector-header-drift.R`, 11
expectations. The collector is JavaScript the R package never executes, so a
test that only grepped the template would pass even if the logic were wrong.
The test runs the real `doPost()` in V8 against a mock of the Sheets API,
replaying the exact scenario above. `V8` joins Suggests as the engine, guarded
with `skip_if_not_installed()`, alongside 1 structural assertion that runs
unconditionally. Mutation-checked: the pre-fix collector fails 6 of the 11.

## Bug, FIXED 2026-08-27: `%in%` branching rules are dead in every exported survey

Found 2026-08-27 while re-platforming the AIC-RSAM instrument
(`AI_Room_service`) onto 0.4.0. **Predates 0.4.0**: the line dates to
0.3.0, so every release since has shipped it.

`sf_branch()` accepts a character vector for `value`, and
`validate_sframe()` passes it without complaint. A vector serialises to a
JSON array. But `evaluate()` in `inst/static_survey/template.html` handles
`%in%` as:

```js
case'%in%':return value.split(',').map(function(s){return s.trim();}).includes(String(actual));
```

Arrays have no `.split`, so the rule throws
`TypeError: value.split is not a function`, `isVisible()` comes back
falsy, and **the gated item stays hidden permanently**. Confirmed in
headless Chrome against a real exported instrument:

```
typeof rule.value        object      (Array.isArray -> true)
evaluate('%in%', ...)    THROWS: value.split is not a function
same rule, comma string  true
```

Impact is total for any instrument that gates on a multi-value `%in%`
rule. In the AIC-RSAM eligibility cascade it made the entire main
questionnaire unreachable: once the gating item was answered, the
remaining screening items, the profile block and all six construct
sections stayed hidden, with no error surfaced to the respondent or the
researcher. The failure is silent at every layer, which is what makes it
worth a patch release: the R side validates clean, the export succeeds,
and the survey renders. It just never shows the questions.

`inst/builder/survey_builder.html` carries the same `value.split` line and
needs the same treatment.

**Fix options**, in preference order:

1. Make the renderer accept both shapes:
   `var vals = Array.isArray(value) ? value : String(value).split(',');`
   Handles every already-written `.sframe` in the field, including files
   an author cannot re-export.
2. Join on the R side in `sf_branch()` so `value` always serialises as a
   scalar string. Cleaner contract, but silently changes the stored shape
   and does nothing for existing files.

Do both: (1) so old files start working, (2) so new files are
well-formed. Add a `validate_sframe()` check that flags a `%in%` rule
whose `value` the renderer cannot consume, since the whole reason this
survived three releases is that nothing ever said a word.

Regression test: export an instrument with a multi-value `%in%` rule,
assert the gated item is visible once the controlling item holds a
matching value. A unit test on `evaluate()` alone would not have caught
it, because the defect is in the R-to-JS serialisation boundary.

### Resolution, 2026-08-27

Report confirmed in full, and the defect is **wider than reported**. It is
not 1 broken evaluator but 3 that disagree, and only 1 of the 6
combinations of evaluator and value shape was ever correct:

| Evaluator | Vector value | Comma string |
|---|---|---|
| `template.html` JS | **throws** | works |
| `sframe_module_eval_op()` (`R/survey_module.R`) | **first element only** | works |
| `.evaluate_branch()` (`R/render_survey.R`) | works | **never matches** |

`sframe_module_eval_op()` is the second live instance and was not in the
report. It does `strsplit(value, ",\\s*")[[1]]` on what is already a
character vector, so `[[1]]` takes the first element and the rule matches
only its first value. That path serves the Shiny survey module, and it
fails silently rather than throwing, so it is the harder of the 2 to
notice.

**Fix option 1 taken, option 2 deliberately declined.** Option 2, joining
on the R side so `value` always serialises as a scalar string, would
contradict `sf_branch()`'s own documentation, which states "For `%in%`,
supply a character or numeric vector", and it introduces a defect of its
own: a value containing a comma, `c("Yes, definitely", "No")`, joins to
`"Yes, definitely,No"` and splits back into 3 values. The array is the
better contract precisely because it has no delimiter to collide with.
Since the renderers have to accept both shapes anyway for files already in
the field, option 2 buys consistency at the cost of correctness. The array
stays canonical.

What changed:

- `sframe_branch_in_values()` in `R/sf_branch.R`, one helper all 3 R paths
  now share, matching the JS. Splits only a length-1 value, so both shapes
  work and neither has to be guessed at.
- `inst/static_survey/template.html`, `evaluate()` accepts arrays and
  strings. Re-inlined into `inst/builder/survey_builder.html` with
  `data-raw/inline_static_template.R` rather than hand-edited, so the 2
  copies stay single-sourced.
- `R/survey_module.R` and `R/render_survey.R` wired to the helper.
- `validate_sframe()` gains a `branching_values` check.
- `tests/testthat/test-branching-in-values.R`, 32 expectations.

Verification:

- Every fix mutation-checked. Reverting any 1 of the 4 fails the test that
  covers it, and restoring returns 32 of 32.
- End to end in headless Chrome, driven by clicking the real radio rather
  than by reading the DOM, which is what the house rule asks for. Before
  the fix the gated item stayed hidden for all 4 answers. After it, it
  appears for `chef`, `manager`, and `server`, and stays hidden for
  `guest`. Screenshot read back: the gated question renders and the
  progress bar counts it.
- Full suite: FAIL 0, PASS 2023, up from 1991. No existing test broke,
  which matters because 3 evaluators changed behaviour.

**A `%in%` rule written before this release needs no re-export.** The
renderers now accept the array those files already carry.
